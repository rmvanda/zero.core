# Module Design Philosophy

When creating modules for Zero Framework, prioritize **utility and fun** over complexity.

## Good Module Characteristics

- **Daily use case**: Solves a real problem you or others face regularly
- **Appropriate complexity**: Lines of code justified by value provided
- **Integration opportunities**: Works with existing modules when sensible
- **Mobile-friendly**: Practical tools work everywhere
- **SEO potential**: Developer tools drive organic traffic

## Red Flags (Over-Engineering)

- Building elaborate systems for simple needs
- Focusing on "impressive" over "useful"
- Creating features without clear use cases
- Losing the fun factor in pursuit of professionalism

## Examples

- ✅ **Good**: JSON formatter (daily use, drives traffic, simple)
- ✅ **Good**: Habits tracker (fun, useful, visual feedback)
- ✅ **Good**: API tester (complements ApiConfig, practical)
- ❌ **Over-engineered**: Tech Stack Explorer (4,000 lines for resume skills section)
- ❌ **Over-engineered**: TTRPG module (10-table database when asked for frame files)

**Remember**: A module can be simple and still showcase framework capabilities. Elegance beats complexity.

## Before Creating a Module

Ask yourself:
1. Will I (or others) use this regularly?
2. Is the complexity justified?
3. Am I solving a real problem or showing off?
4. Is this fun to build AND use?

When in doubt, start simple. You can always expand later.
